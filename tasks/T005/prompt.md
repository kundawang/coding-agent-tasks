我们做现场设备巡检。盒子上跑两个进程：采集进程把传感器读数落到本地缓存，上报进程定期把"还没上报过"的记录
发到云端，发成功之后标记掉。盒子都在户外，网络时断时续，也经常被人直接拔电。

现在的做法是每天一个 JSONL 文件 + 一个 .sent 标记文件，这一年出了好几次事，我把事故记录整理在
samples/incident-notes.md 里了，你先看那个，新存储要能扛住上面写的每一类事故。

仓库里现在只有 samples 和这份说明，代码你从零写。数据模型的字段含义、目录约定、命令入口在 README.md 里。

下面是我要的：

1、追加的原子性和持久性。append 一批记录，**函数返回之后这批数据就必须已经落盘**：之后任何时刻拔电，
重启回来这批记录一条不能少。同一批要么全部生效要么全部不生效，不能出现"一半进去了"。这是最硬的一条，
你要在设计里写清楚"什么时刻算持久"，以及为此付出了什么代价。

2、幂等去重。dedupKey 全局唯一，重复 append 同一个 key 只保留一条，后到的丢掉；丢掉多少条要能在 stats 里看到。

3、多进程同时跑。上报进程在读、可能还在做回收，采集进程同时在写；接单量大的时候还会再起第二个采集进程。
这些组合任意出现，都不能把数据写坏、不能读到半条记录。互斥要用文件系统原语做（例如以独占方式创建锁文件），
不能假设"同一时刻只有一个写者"。

4、范围扫描要有序、而且要快。scan 按 ts 升序返回 [from, to) 内的记录（ts 相同的按写入先后），
支持只要未上报的、支持 limit。**扫描不能每次把整个文件读一遍再解析一遍**——我们一台盒子上攒到过 80 万条，
那种做法顶不住。每条记录要有存储层分配的稳定 id，供标记使用，重启之后不能变。

5、已上报标记。mark-sent 把若干 id 标成已上报，必须幂等、而且必须持久：标记写入返回之后拔电，
重启回来不能再把它们扫出来。上报是"至少一次"，标记丢一次就意味着云端收到重复数据，这条不能马虎。

6、崩溃恢复。任意时刻被 kill -9 或者断电，重新打开必须成功；已经成功返回的 append 一条不能少；
如果尾部留了写了一半的数据，要能识别出来、跳过它继续工作，并且把这件事记下来让 verify 能报告出来——
老方案就是卡在这里，第二天采集进程直接起不来。

7、回收。已经上报、且 ts 早于给定水位的数据要能被回收掉，文件不能无限涨。回收过程中**未上报的数据
一条都不能丢**；回收本身要能被打断，下次能接着做，不能一次失败就把存储搞成永久不可用。

8、可诊断。verify 要检查存储完整性并给出结论：健康还是受损、损伤在哪、还能救回多少，退出码要能区分两种情况。
stats 要给出：记录总数、未上报数、去重丢掉的数量、最早/最晚 ts、占用空间。

9、格式要能对外解释。上报端是一个 Go 小程序，它会**绕过你的代码，直接按约定的文件格式只读地读**这些数据。
所以不能把数据塞进现成的容器里（Node 的 node:sqlite 也不许用），格式得是你自己设计、能写进 FORMAT.md
让另一个语言照着实现的东西：文件怎么分段、每条记录怎么定界、校验怎么算、怎么判断一条记录是完整的、
回收之后布局怎么变，都要写清楚。

10、性能。批量追加 20 万条、再全量扫一遍，都要能实际跑完。别一条记录 fsync 一次，那样根本跑不动——
需要考虑组提交之类的办法。给一个 bench 子命令输出耗时。

约束：

- 只用 Node.js 内置模块（node:fs / node:path / node:crypto / node:test 等）。不许 npm install、
  不许引入任何第三方库、不许起本地服务或数据库。
- 存储目录里可以有多个文件，但每个文件都要自解释、可回收。
- 不许图省事把整个存储每次读进内存再整体写回，80 万条会撑爆盒子。
- 测试用 node --test；崩溃相关的用例要**真的起子进程再 kill -9**，不能只打桩。
- samples/ 里的文件不要改。

交付：

- bin/edgejournal.js、src/、FORMAT.md、test/
- README.md 顶部补一节"怎么用"，写清命令，以及**持久性边界**：什么情况下 append 返回后一定不丢、
  你们选的 fsync / 组提交策略是什么。

下面这套流程必须能一条条跑通：

    node bin/edgejournal.js append var/store --input samples/records.jsonl
    node bin/edgejournal.js stats  var/store
    node bin/edgejournal.js scan   var/store --from 1789700000 --to 1789700200 --limit 5
    node bin/edgejournal.js verify var/store
    node bin/edgejournal.js compact var/store --before 1789700200
    node bin/edgejournal.js verify var/store

另外 `node --test` 要全绿。scan 每条输出一行 JSON，在原始字段之外多一个 `_id` 字段（存储层分配的稳定 id）。
