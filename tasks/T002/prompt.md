我们要给内部构建系统加一个离线的依赖解析模块 depgraph。当前目录只有骨架和样例数据，代码从零写。它不联网，输入是一份包索引和一组根依赖，输出一份确定的安装方案；解不出来的时候要说清楚为什么解不出来。

模块名就叫 depgraph，入口是 python -m depgraph solve <index.json> <requirements.txt>。

一、版本和约束

1. 版本号是 MAJOR.MINOR.PATCH，可以带预发布后缀，例如 1.2.0、2.0.0-rc.1、1.0.0-alpha.beta。
2. 版本比较：先比主、次、修订号（按数值大小）；预发布版本比同号的正式版小（2.0.0-rc.1 < 2.0.0）；两个预发布版本之间逐段比较，纯数字段按数值比，含字母的段按字典序比，段数少的更小（1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta）。
3. 约束支持 *、=1.2.3、>1.2.3、>=1.2.3、<1.2.3、<=1.2.3、^1.2.3、~1.2.3；多个约束可以用逗号连起来取交集，例如 ">=1.0.0, <2.0.0"。
   - ^1.2.3 表示 >=1.2.3 且 <2.0.0；^0.2.3 表示 >=0.2.3 且 <0.3.0；^0.0.3 只允许 0.0.3 这一个版本
   - ~1.2.3 表示 >=1.2.3 且 <1.3.0
   - * 表示任何正式版
4. 预发布版本默认不参与选择，只有当某个生效的约束里显式写了预发布版本时它才可能被选中（例如约束是 >=2.0.0-rc.1 时，2.0.0-rc.1 才可以被选）。

二、解析规则

1. 同一个包最终只能有一个版本，不允许同包多版本共存；所有生效约束都要满足，包括传递依赖带进来的约束。
2. 解析策略必须严格按下面这个来，保证同一个输入永远得到同一个结果：
   - 维护一个"待决定"的包集合，初始是根需求里的包；运行中出现的依赖也加进来。
   - 每次取包里名字字典序最小的那个包，在满足它当前全部已知约束（以及预发布、yanked 规则）的候选版本里从高到低试。
   - 选定版本后把它引入的依赖约束并进来，继续解析下一个包；一旦某个包没有任何候选版本，就回退到最近一个还有更低候选版本的决策点换版本。
   - 所有决策点都试完仍然无解，就判定为冲突。
3. 标记为 yanked 的版本不能选，除非根需求里用 =版本 精确点名了它。
4. 依赖成环是合法的，要能正常解析出来。
5. 索引规模不大（最多几百个版本），可以用回溯穷举，不用考虑性能。

三、输出

1. 成功时往 stdout 打印 JSON，退出码 0：
   {"ok": true, "resolution": {"<包名>": "<版本>", ...}, "install_order": ["<包名>", ...]}
   install_order 是安装顺序：被依赖的排前面；可以并行安装的（互不依赖）按包名升序。
2. 解不出来时也往 stdout 打印 JSON，退出码 1：
   {"ok": false, "conflicts": [{"package": "<包名>", "constraints": [{"constraint": "<约束原文>", "required_by": "<包名>@<版本>" 或 "root"}, ...]}], "explanation": "<一句话说明>"}
   conflicts 里每一组必须是**最小冲突集合**：把这组里的任意一条约束拿掉，这组约束就不再冲突。可能有多组冲突，至少给出一组。explanation 要说人话，例如 "driver 没有任何版本能同时满足 service-a@1.0.0 要求的 <2.0.0 和 service-b@1.0.0 要求的 >=2.0.0"。

四、交付要求

1. 只用标准库，Python 3.11+，不要引第三方包。
2. README 补上用法、约定，以及你的设计取舍（尤其是版本比较、预发布过滤、冲突怎么找最小集）。
3. 自带测试，python -m unittest discover -s tests 必须全过；测试要覆盖预发布版本、yanked、依赖成环、冲突最小集这几类情况。
4. samples/ 下两组样例要跑出正确结果：samples/index.json + samples/requirements.txt 能解出方案；samples/conflict_index.json + samples/conflict_requirements.txt 要报出 driver 上的冲突。
