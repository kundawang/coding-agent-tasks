我们内部有一套风控规则引擎 riskmule，上个月刚上线。流程是风控同学写规则集（JSON），引擎对每一笔下单事件
逐条求值，给出 allow / review / deny 三种结果。最近线上出了几笔明显判错的单子，风控同学把当时的事件
捞出来整理到了 samples/ 里，你直接跑这个就能复现：

    python -m riskmule replay samples/ruleset.json samples/events.jsonl

规则集和事件我一个字都没改过，是原始样本，你也不要动它们。

现在观察到的问题，按 replay 输出的序号说：

1、第 1 条：一个注册不到一天的新号，在 h5 渠道下了 9000 的单。规则集里 R-DENY-AMOUNT（非可信渠道大额）
应该把它直接拒掉，但实际只走了 R-REVIEW-NEW-USER 的复核。规则集里 priority 的数值和我们要的先后顺序
是对得上的（数值大的先判），你对照 README 里的口径看看是哪边没做到。

2、第 2 条：设备风险分 85、金额 3000 的单子。R-DENY-RISKY-DEVICE 应该命中——第一个条件"金额大于 2000"
成立，第二个条件"设备风险分 >= 70 或者 卡号 62 开头"里，风险分那半边也已经成立了。结果引擎直接 allow。
这个用户没有绑卡，取不到 user.card.number，我怀疑跟"取不到字段"有关，具体是什么原因你自己看。

3、第 3~10 条是同一个用户连着下 8 单。R-DENY-FREQ 配的是"60 秒内 6 次就拦"，结果这 8 单一条都没拦下来。
这条规则从上线到现在好像就从来没触发过。

4、第 11~14 条：同一个用户在一分钟内累计 1233.76 + 1419.13 + 347.11 = 3000.00。R-REVIEW-AMOUNT-SUM
配的是"超过 3000 才复核"，刚好 3000 是不该进复核的，但第 14 条还是被判了 review。风控同学的要求是
金额一律按两位小数精确比较，不允许出现浮点误差。

5、第 15~22 条是未登录访客。第 21 条访客 A 连点到第 7 次被拦下来，这个是符合预期的；但第 22 条另一个
访客 B 的第一单也被拦了。这两个人不是同一个人，他们的次数不应该混在一起算。

改的时候注意这几点：

- 只改 riskmule/ 里的实现。samples/ 下的规则集和事件是原始样本，一个字都不要动。
- 仓库里现有的 tests/ 是全绿的，说明现有用例没覆盖到上面这些边界。允许你加测试，但不许改现有测试的
  断言、也不许删掉或跳过现有测试来把事情绕过去。
- 不要引入第三方依赖，Python 标准库就够了。
- 对外的调用方式别乱改：Engine.observe / Engine.decide / ruleset.load / ruleset.parse /
  SlidingWindow 的公开方法外面都在用，签名保持兼容。
- README 里写的语义（规则按 priority 从高到低命中即返回、滑动窗口左闭右开、金额精确比较）是产品口径，
  以 README 为准；实现跟 README 不一致的地方，改实现。
- 上面每一条问题都要补一个能卡住它的回归测试。
