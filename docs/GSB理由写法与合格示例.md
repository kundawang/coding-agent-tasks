# GSB 理由怎么写

## 三要素（质检会逐条看）

一条**合格**的原因必须同时具备：

1. **触发节点（When）**：在哪个阶段、哪个环节、哪次工具调用出的问题？
2. **实际行为（What）**：模型具体做了什么？
3. **业务影响（Impact）**：导致什么后果？

再进一步，好的原因还要指出**根因**和**正确做法**。

## 硬性要求

1. **过程与产物都要分析**，分别说清"过程哪里差、产物哪里差"。
2. **定位到具体环节和步骤**：哪个步骤、哪次工具调用、哪次文件改动。
3. **用证据，不用形容词**：引用报错信息、出错的文件名/函数、漏掉的具体需求；
   禁止只写"效果不好/不行/一般"。
4. **只写模型本身能力造成的问题**，不写环境/网络波动导致的工程故障。

## 模板

```
过程问题：
在【第几步/哪个环节】，模型【做了什么具体行为】→ 导致【什么后果】
（→ 【根因和正确做法】）

产物问题：
产物在【哪个文件/功能】存在【什么具体问题】，表现为【客观证据，如报错/缺失需求】，
无法满足【哪条需求】。

闭环表述（产物问题由过程问题导致时）：
在【第几步/哪个环节】，模型【做了什么具体行为】→ 导致产物在【哪个文件/功能】存在
【什么具体问题】，表现为【客观证据】，无法满足【哪条需求】，（→【根因和正确做法】）。
```

## 针对本项目的额外要求

- **A 和 B 分别写。**不要只写"A 比 B 好"就收尾；两次跑往往各有优劣，
  要分别说清各自好在哪、不好在哪，是产物还是过程。
- **最后说明你更偏好哪一次、基于哪几点判定的**，体现你的权衡与个人偏好。
- **选 Same 时同样要写详细。**Same 不是"看不出差别"的兜底选项，
  要写清两边在哪些点上确实等价、哪些点上各有优劣相互抵消。**一句话的 Same 会被直接拒收。**

## 找问题的方向

### 过程类常见问题

| 类别 | 典型表现 |
|---|---|
| 指令遵循 | 忽略明确约束、漏做部分需求、做了没要求的额外改动、擅自改技术栈 |
| 任务规划 | 无规划/规划错误、步骤顺序混乱、目标漂移、来回反复、该问不问 |
| 工具使用 | 参数错误、改文件前不先读、同一失败调用反复重试、不会用搜索 |
| 幻觉 | 编造不存在的 API/参数/配置项，臆造 repo 里的文件/函数，声称做了实际没做的事 |
| 验证缺失 | 没跑测试就说完成、对报错视而不见、不检查输出 |
| 纠错能力 | 死循环、重复同一种无效修复、遇困难就放弃 |
| 交互沟通 | 该问不问/乱问、进度汇报误导、缺阶段性总结 |

### 产物类常见问题

| 类别 | 典型表现 |
|---|---|
| 正确性 | 编译/运行失败、逻辑错误、边界 case 挂、引入回归 |
| 完整性 | 漏需求、半成品、留 stub/TODO |
| 代码质量 | 可读性差、无错误处理、结构差、违反 repo 规范 |
| 过度工程 | 无意义的高复杂度、多余文件 |
| 偷工减料/造假 | 硬编码、假数据、删/改测试来 hack、占位实现 |
| 破坏性 | 删改无关代码、破坏既有功能 |
| 安全 | 引入漏洞 |
| UI/美观度 | 难看、与设计不符、布局错乱 |

## 合格 / 不合格对照

| ❌ 不合格（一定会被拒收） | ✅ 合格 |
|---|---|
| "没完成任务，不满意" | "prompt 要求支持分页，产物只实现了列表查询，完全没动分页参数，产物不完整。" |
| "代码有 bug" | "产物 utils/date.py 的 parse() 未处理时区，输入带 Z 的 ISO 串会抛 ValueError。" |
| "（一段意味不明的报错信息）" | "在第 3 步用 edit_file 改 auth.py 时引入了未定义变量 token，且未运行就宣称完成，导致代码报错。" |
| "过程比较乱" | "规划混乱：模型在第 2、4、6 步三次重复读取同一个 config.py，且第 5 步改完没运行就宣称完成，存在验证缺失。" |
| "效果还行但不满意" | "任务虽完成，但模型臆造了 lodash.deepMerge（实际不存在该方法，应为 merge），仅因该分支未被执行才没报错，属于幻觉。" |
| "思考超限需要人工继续" | "效率差：一个单文件改动用了 18 步，其中 9 步是反复试错式的 grep，且触发一次思考超限需人工『继续』。" |
| "文件没改成功，一直在报错。" | "在修改 utils.py 时，模型没有先使用 Read 工具读取文件，就直接尝试 SearchReplace，导致匹配不到对应代码而报错，模型应该在修改任何已有文件前先 Read 获取最新上下文。" |
| "写的代码根本不符合我的需求。" | "任务是『优化当前页面的加载速度』。模型花了很多步骤去改后端的数据库查询（实际行为），但我明确在提示词里说过『只允许修改前端缓存逻辑』（违反的约束）。期望模型在规划阶段严格遵守作用域限制。" |
| "越改问题越多。" | "在终端返回 npm install 的版本冲突错误后，模型连续 3 次尝试了完全相同的安装命令。期望它在遇到此类错误时能主动读取 package.json 检查依赖版本，而不是盲目重试。" |

## 样例一：微信小程序图片调色板（GSB 结论：B 更好）

**题目信息**：任务类型 `0-1代码生成`｜难度 `困难`｜语言/框架 `微信小程序原生框架、JavaScript、WXML、WXSS、JSON`｜Harness `Claude Code 2.1.273`｜操作系统 `MacOS/Linux`｜环境可复现等级 `有外部依赖，未容器化`

**GSB 理由原文**：

> A 的问题发生在模型生成 app.json 时，把 chooseMedia 写进了 requiredPrivateInfos，但微信只允许
> chooseAddress、chooseLocation 等字段，结果小程序在 app.json 解析阶段就报 requiredPrivateInfos[0]
> 字段错误，导致 A 完全无法启动，后续网格、调色板等功能都无法看到；B 的问题首先是导入图片后走 OCR
> 分支时，模型在 image-loader.js 对离屏 Canvas 直接调用 canvas.toTempFilePath，但页面在 index.js
> 创建的是 wx.createOffscreenCanvas，当前基础库没有这个方法，且错误在 img.onload 异步回调中抛出，
> 导致导入和识别流程中断。其次是手动调整网格点击应用时，onAdjustConfirm 进入 buildPaletteByCluster，
> 模型在 index.js 把空数组 [] 传给 updatePaletteView，而代码中却按 Map 调用 counts.get，导致
> counts.get is not a function。综合判断我更偏好 B，主要依据是 A 在启动阶段就因非法 app.json 直接失败，
> 任何功能都无法验证，而 B 至少能启动、能进入导入和手动调整流程，不过 B 目前导入主流程和手动应用也都
> 报错，所以两者都还未达到可交付状态。

**看点**：两边都分别写了问题（文件 + 报错 + 后果），最后给出偏好与权衡依据。

## 样例二：家庭装修施工顺序沙盘（GSB 结论：A 更好）

**题目信息**：任务类型 `0-1代码生成`｜难度 `困难`｜语言/框架 `TypeScript, React, Vite, SVG, Vitest`｜Harness `Claude Code 2.1.98`｜操作系统 `MacOS/Linux`｜环境可复现等级 `无外部依赖`

**GSB 理由原文**：

> A 的过程整体更聚焦：模型先实现图算法、排程和修复模块，再通过 npm test 暴露破环规则、施工日历与
> 关键路径断言问题，修正后继续完成 UI，并在结束前跑通类型检查、36 项测试、生产构建和开发服务。产物方面，
> A 完成了任务编辑、七类冲突检测、SVG 甘特图拖拽与工期调整、关键路径、基线对比、延期原因、撤销重做、
> 持久化和 JSON 导入导出；把"全屋拆除"工期从 2 天改为 5 天后，"水电定位开槽"从第 2 天移动到第 8 天，
> "厨卫水电布管"从第 2 天移动到第 7 天，说明依赖传播实际生效。A 的问题出在实现 src/lib/repair.ts 的
> 修复计划时，模型把"不能覆盖用户手动锁定任务"处理成可以在预览后自动解锁责任任务，代码会将 pinned
> 改成 false 并清空 pinnedStartDay。默认示例生成修复计划时明确提出解锁"灯具与开关安装"，并把它从
> 09-26 移动到 10-23，确认应用后会改变用户设置的锁定状态和日期。
>
> B 的过程验证范围更广，模型完成了 46 项测试、TypeScript 检查、构建、整页渲染冒烟检查和本地 HTTP 访问；
> 其修复计划也能保留锁定任务，默认示例从 20 个冲突降到 3 个，并对无法移动的"竣工验收"给出人工处理提示，
> 这一点优于 A。但模型在编写 src/engine/scheduler.ts 时主动加入了"所有非空开始日期均保持不动"的规则，
> 而内置示例中的任务都设置了固定 start，新增任务也默认使用 start: 0。把"全屋拆除"工期从 2 天改为 5 天后，
> "厨房水电改造"和"卫生间水电改造"仍停留在第 2 天，没有沿依赖关系顺延，只会新增前置冲突，用户要求的
> 依赖传播在默认操作流程中没有实现。B 的关键路径展示也存在明确错误：页面显示"关键路径 1 项·共 19 天"，
> 只有"竣工验收"被标为关键任务；原因是 src/engine/criticalPath.ts 使用 Math.max(bestLen, projectFinish)
> 把整个项目结束日当成这条单任务路径的长度，导致关键任务数量与路径工期不一致。模型虽然测试了人工构造的
> 关键路径用例，却没有检查内置示例页面上的最终展示，测试通过后仍按完成收尾。
>
> 综合来讲，B 在锁定任务保护和测试覆盖上更好，但依赖传播是施工沙盘的核心日常编辑能力，B 在默认示例和
> 新增任务中都无法实现，同时关键路径结果存在明显矛盾。A 的自动解锁问题只在用户生成并确认修复计划时触发，
> 预览会明确展示修改并支持撤销；A 在依赖传播、甘特交互和核心排程上的完成度更高，因此选择 A 更好。

**看点**：过程与产物分开写、A/B 分开写、每条问题都落到具体文件与行为，最后给出明确的权衡与结论。
