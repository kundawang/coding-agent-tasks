<callout emoji="💡">

</callout>

</callout>

### 第二步：出题并记录必要信息

1. **出题并记录初始快照。**题型范围、分布偏序关系不变；本期只跑首轮，**简单、中等难度的提示词一律禁止**。出好题后在工作区提交一次，拿到 40 位完整 SHA 的 commit permalink，作为两次模型执行的共同起点。
2. **第二步，跑第一次（A）。**用 auto 模型跑，只跑首轮，模型给出回答后本轮即结束，不要追问、不要纠错，跑完后提交产物拿到 A 的产物快照，录一段运行录屏，记下 SessionID，导出本次的轨迹 jsonl。
3. **第三步，把工作区重置初始环境。**恢复初始环境，并清掉 node_modules、venv、构建产物这类未跟踪文件。
4. **第四步，跑第二次（B）。**使用**完全相同**的 prompt、**完全相同**的 Harness 和版本、相同的机器和操作系统，同样只跑首轮。产出与第二步一致。

> 录屏的目的是证明产物真实性，以及专家确实对产物有所衡量。所以录的是**产物的实际运行**，两次跑各录一段，要求如下：从干净状态启动，完整展示真实输出；**无法运行的也必须录，把报错过程录出来**；不要剪掉失败或不好看的片段；时长控制在 90 秒以内，提交到录屏附件中

### 第三步：写GSB

对比两次跑的过程与产物，选出你更满意的一次，并按下方「GSB 理由怎么写」的要求写明理由，**体现专家个人的偏好。**

- **要说明偏好的判定依据。**写清**你在意什么，你更满意哪一次、是基于哪几点做出的判断**。两次跑往往各有优劣，要体现出你是怎么权衡的，而不是给一个没有来由的结论。
- **A 和 B 分别写。**不要只写"A 比 B 好"就收尾，要分别说清两次跑好在那里，不好在哪里，是产物还是过程，如果是过程，问题出在哪一步（触发节点）、模型具体做了什么（实际行为）、导致了什么后果（业务影响），如果是产物，指向具体的文件名、报错信息或未实现的需求点。
- **选 Same 时同样要写详细。**Same 不是"看不出差别"的兜底选项，要写清两边在哪些点上确实等价、哪些点上各有优劣相互抵消。一句话的 Same 会被直接拒收。

<callout emoji="💡">
**注意：一定要保持窗口中只有提示词，不要输入其他除提示词外的内容。如果遇到api error、网络波动、504等情况，需要新开窗口跑提示词！！！**
</callout>

- **推理的时长：**可能受模型部署影响。不要把推理时长考虑进去，对于效率的衡量可以看轮次和篇幅。

- **网络工程错误（有报错）：**不考虑网络波动、请求失败这类工程故障。遇到了重开新窗口。

# 存档：如何写好不满意原因

<callout emoji="💡">
在提交不满意原因时，请先在脑海中问自己三个问题，想清楚：
1. **“模型是从哪一步开始降智的？”**
2. **“模型的具体什么操作让我觉得很弱智？”**
3. **“换做是一个人类高级工程师，遇到这种情况会怎么做？”**
</callout>

---

### “不满意原因”的硬性要求（质检会看）

```Plain Text
1. 过程与产物都要分析，要分别说清"过程哪里差、产物哪里差"。

2. 定位到具体环节和步骤：指明问题发生在哪个步骤、哪个工具调用、哪次文件改动。

3. 用证据，不用形容词：引用报错信息、出错的文件名/函数、漏掉的具体需求；禁止只写"效果不好/不行/一般"等笼统的表面症状。

4. 只能写由模型本身能力造成的问题，不能写环境/网络波动导致的问题，例如模型请求失败。
```

---

### 写作方法参考

<callout emoji="💡">
一条**合格**的原因必须同时具备三要素：
1. **触发节点（When）**：在哪个阶段或哪个动作出了问题？
2. **实际行为（What）**：模型做错了什么？
3. **业务影响（Impact）**：这个错误导致了什么后果？
**一条好的原因，除此之外还需要能够指出模型错误行为的根因和正确做法。**
一条数据可能存在很多个问题点，每一点都应按三要素展开说明，写作格式无需完全一致（不作为质检点），但是上述硬性要求都需要踩到（作为质检点）。
</callout>

```Plain Text
过程问题： 
在【第几步/哪个环节】，模型【做了什么具体行为】→ 导致【什么后果】（→ 【根因和正确做法】）

产物问题： 
产物在【哪个文件/功能】存在【什么具体问题】，表现为【客观证据，如报错/缺失需求】，无法满足【哪条需求】。

产物问题可能是由过程问题导致的，这时可以是更为完整闭环的表述：
在【第几步/哪个环节】，模型【做了什么具体行为】→ 导致产物在【哪个文件/功能】存在【什么具体问题】，表现为【客观证据，如报错/缺失需求】，无法满足 【哪条需求】，（→ 【根因和正确做法】）。
```

| 指令遵循 | 模型是否严格遵守了用户在 Prompt 中明确提出的所有约束条件（如：特定库的使用、代码风格、禁止修改的文件等）？是否存在忽略明确约束、漏做部分需求、做了没要求的额外改动、擅自改技术栈等行为？ |
| 任务规划 | 模型是否能合理拆解任务？是否有清晰的阶段性状态追踪？遇到歧义时是否主动求问？是否有阶段性总结或反馈？是否无规划/规划错误、步骤顺序混乱、目标漂移、来回反复？ |
| 工具使用 | 模型是否能够调用合理的工具？是否出现了参数错误，改文件前不先读、同一失败调用反复重试、不会用搜索等问题？ |
| 幻觉 | 模型是否出现幻觉？是否编造看似合理、实则不存在的 API/参数/配置项，或臆造了 repo 里的文件/函数，声称做了实际没做的操作？ |
| 验证缺失 | 模型是否没有执行合理的测试验证就说完成？是否对报错视而不见、不检查输出？ |
| 纠错能力 | 模型陷入死循环、重复同一种无效修复、或者遇到困难就轻易放弃？ |
| 交互沟通 | 该问不问/不该问乱问、进度汇报误导、缺乏阶段性总结等 |

1. **产物类常见问题**

| 类别 | 典型表现 |
|-|-|
| 正确性 | 编译/运行失败、逻辑错误、边界 case 挂、引入回归 |
| 完整性 | 漏需求、半成品、留 stub/TODO |
| 代码质量 | 可读性差、无错误处理、结构差、违反 repo 规范 |
| 过度工程 | 无意义的高复杂度、多余文件 |
| 偷工减料/造假 | 硬编码、假数据、删/改测试来hack、占位实现 |
| 破坏性 | 删改无关代码、破坏既有功能 |
| 安全 | 引入漏洞 |
| UI/美观度 | 难看、与设计不符、布局错乱 |
