## 1. 项目目标

还原真实用户在使用 Coding Agent 过程中产生的反馈信号，用来判断模型是否真正满足了用户需求，
并作为后续模型训练与持续优化的数据。为此要标注一批**真实使用过程中的环境、轨迹与高质量用户反馈**。

## 2. 数据形态（最核心的一条）

| 条目 | 本期要求 |
|---|---|
| 数据形态 | **一道题跑两次 = 一条 pair-wise 数据** |
| 模型 | 使用 auto 模型，不自行指定 |
| 轮次 | **只跑首轮，不做任何追加交互**；每一个 session 仅可进行一轮有效交互 |
| 评价方式 | GSB 结论 + 一段对比理由 |
| 产物证明 | 轨迹 + 初始环境快照 + 产物快照 + **运行录屏** |
| Harness | **Codex CLI** |

## 3. 两次跑的"同一起点"要求

两次跑之间**只允许模型本身存在差异**。以下必须完全一致：

- 同一台机器、同一操作系统、同一环境
- 同一个 Harness（客户端）与**同一个 Harness 版本**
- **完全相同的 prompt**（原文粘贴，不摘要、不改写）
- 完全相同的配置，包括 **max context token = 1000000**

任何环境、配置、prompt 上的差异都会导致这条数据作废。

## 4. 作业流程

### 第一步：接入模型

用项目方给的配置脚本（`docs/vendor/codex-cli-setup.sh`）接网关。

- 脚本会把 `max context token` 配成 **1000000**，**不要自行修改，也不要删它生成的两个文件**
  （`~/.codex/relay_model_catalog.json`、`~/.codex/relay_base_instructions.txt`），
  删掉会让实际窗口掉回 258400，跑出来的结果不算有效。
- 作业前自查上下文窗口确认无误再开始。
- 全程使用 auto 模型，两次跑之间**不要改动任何配置**。

### 第二步：出题并记录必要信息

1. **出题并记录初始快照。**工作区准备干净后提交一次，拿到 **40 位完整 SHA 的 commit permalink**，
   作为两次模型执行的**共同起点**。
2. **跑第一次（A）。**用 auto 模型跑，只跑首轮；模型给完回答本轮即结束，**不追问、不纠错**。
   跑完提交产物拿到 **A 的产物快照**，录一段运行录屏，记下 SessionID，导出本次轨迹 jsonl。
3. **把工作区重置回初始环境。**并清掉 node_modules、venv、构建产物这类未跟踪文件。
4. **跑第二次（B）。**使用**完全相同**的 prompt、Harness 和版本、机器和操作系统，同样只跑首轮。

### 第三步：写 GSB

对比两次跑的过程与产物，选出你更满意的一次，并写明理由，**要体现专家个人的偏好**。
写法与合格示例见 `GSB理由写法与合格示例.md`。

## 5. 快照与轨迹的硬性要求

| 项 | 要求 |
|---|---|
| 初始环境快照 | commit permalink，**40 位完整 SHA**，两个产物快照的**父提交**必须是它 |
| A/B-产物快照 | 本次跑结束后的 commit permalink，**40 位完整 SHA** |
| A/B-SessionID | 本次跑的会话 ID，两次是两个不同的会话，各填各的 |
| A/B-轨迹文件 | 把 `~/.codex/sessions/`（或 `~/.claude/projects/`）下对应的 **jsonl** 上传到对象存储，填可直接下载的链接 |

跑 B 之前必须 `git reset --hard` 回到初始环境 commit，并清掉 node_modules 等未跟踪产物 ——
这是核验两次跑是否同起点的依据，忘了重置会被判「作废-环境未重置」。

## 6. 运行录屏要求

- **两次跑各录一段**；录的是**产物的实际运行**，不是讲解。
- **从干净状态启动**，完整展示真实输出。
- **无法运行的也必须录，把报错过程录出来**；不要剪掉失败或不好看的片段。
- 时长 **90 秒以内**，**720p，mp4**。
- **录制内容要和 GSB 描述内容对应上**：
  - 前端项目：需要展示错误的问题，并与描述内容对应；
  - 后端项目：可以录启动过程，或运行测试文件。
- 目的是证明产物真实性、以及专家确实对产物有所衡量。

## 7. 不应该考虑的因素

- **推理时长**：可能受模型部署影响，不要把推理时长算进去；衡量效率看**轮次和篇幅**。
- **模型戛然而止（无报错）**：可能受部署和 harness 适配影响。遇到了**重开新窗口**；
  如果一直无故中断就换题目。
- **网络工程错误（有报错）**：不考虑网络波动、请求失败这类工程故障。遇到了**重开新窗口**。
- **禁止使用 AI 工具分析轨迹与产物、或代写 GSB 理由。**

## 8. 时限与红线

- **当天 20:00 前**执行任务产生的数据**必须当天提交**；**20:00 后**产生的数据允许**次日 14:00 前**提交。
- **所有数据不允许返修**；不符合质量要求的数据**直接拒收**。
- 被项目方抽检发现高频不合格数据 → **这位专家的历史数据全部拒收**，不允许继续参与项目。
- **严格禁止使用 AI 工具分析产物与轨迹**；使用 AI 标注的专家，**一经发现拒收全部历史数据**，
  禁止再次参与项目。
- 高度相似的题目（环境几乎相同 + 任务几乎相同）**只接收一条**，其余拒收。
  禁出题库见 `雷同题黑名单.md`。

## 9. 题型分布要求

**任务类型**（单选，7 类）：`0-1 代码生成` / `Feature 迭代` / `Bug 修复` / `代码理解` /
`代码重构` / `工程化` / `代码测试`

**任务难度**（单选）：本期**只跑首轮，严禁出简单题、中等题**，只允许

- **困难**：需要整合多个模块/系统约束，做关键设计取舍，处理复杂状态、兼容性、权限、并发、性能或异常链路。
- **地狱**：人执行起来需要极高的决策复杂度，通常需求很开放或约束很隐蔽，需要极深的项目理解、
  架构级判断、多步复杂的调试验证，或正确性依赖大量边界场景。即使当前 SOTA 模型也无法成功交付。

## 10. 易踩的坑（自查清单）

跑之前：

- [ ] 确认 Codex CLI 实际上下文窗口 = **1000000**（看最新 rollout 里的 `model_context_window`）。
- [ ] 确认两次跑用**同一个** Harness 版本；中途升级过 CLI 就不要拿升级前的 A 去配升级后的 B。
- [ ] 初始环境快照已经提交并拿到 **40 位完整 SHA**（在首轮开始前完成）。
- [ ] 题目不在雷同题黑名单里，难度是困难/地狱。
- [ ] 工作区开跑前是干净的（没有残留上一个题的产物）。

跑 A / 跑 B 时：

- [ ] **对话窗口里只有 prompt**，不要输入任何其他内容。
- [ ] 遇到 api error / 网络波动 / 504 / 无报错中断 → **新开窗口重跑**，不要在同一个 session 里继续。
- [ ] 只跑首轮，**不追问、不纠错**；一个 session 只用一轮。

跑完之后：

- [ ] 立刻提交 A 的产物快照（否则 A 的产物会被 B 覆盖，没法还原）。
- [ ] 重置工作区回初始快照，并清掉未跟踪文件，再跑 B。
- [ ] 拿到 A/B 的 SessionID，并导出两条 jsonl 轨迹。
- [ ] 两段录屏都满足 90 秒 / 720p / mp4 / 从干净状态启动。
- [ ] 记录过的 SHA **不要 amend / rebase / force-push**，否则 SHA 不可达，数据会被打回。
- [ ] 只用 40 位完整 SHA，不要用短 SHA、分支名或 tag 代替。
- [ ] 提交前确认 `语言/框架`、`Harness 版本`、`环境可复现等级` 这些容易漏填的字段都填了。
- [ ] 提交时间在时限内（20:00 前当天交，20:00 后次日 14:00 前交）。
